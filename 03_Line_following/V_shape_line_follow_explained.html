V-Track Line Follower: How It Works

CS413 Robotics · Lab 03 Line following · V_shaped_line_follow_sim.qrs / V_shaped_line_follow_real.qrs

Short version. The program is one TRIK Studio block diagram: an Init function block, then a loop of Function block → two Motor blocks → Timer (10 ms).
  • It follows the line with a nonlinear PD controller using two light sensors: A3 = left, A4 = right.
  • The sensor range calibrates itself while driving.
  • A small state machine handles sharp V tips and corners:
    • a "junction lock" remembers which side the line went;
    • an encoder-limited pivot search finds the new branch without turning back onto the line it came from.
  • In the 2D simulator it completes the whole track (both V tips and both 90° corners) in 62 s with ideal settings.
  • With realistic noisy sensors, motors and physics it succeeds in about 94% of random runs.
  • The structure matches what classmates ran successfully on the real robot: same ports, same error sign, same motor mapping.

1. Task and result

Goal: make the robot in V_shaped_2D_line_follow.qrs drive along the whole V-shaped line in the 2D simulator. The program also has to work on the real TRIK robot.

The original file was not changed. Two new files were added:

V_shaped_line_follow_real.qrsSame program, for uploading to the real robot. The program itself is identical; only the use differs.

What changed compared to the original file:

  • Sensor ports. The original simulated sensors were on A1/A2. They are now on A3 (left) and A4 (right), which is how the class robots are wired. This was changed both in the world and in the robot's device configuration.
  • Start pose. In the original, the robot started near the left vertical segment instead of at the beginning of the line. Now its centre is at (−455, −107) and it faces 142° along the first diagonal.

2. The track and why it is hard

The line is a closed-looking shape with five segments (sim coordinates; y points down):

(-455,-107) → (-615, 17)      diagonal down-left    → V1 tip
(-619, 17)  → (-617,-326)     up the left side      → top-left 90°
(-617,-329) → (-152,-334)     across the top        → top-right 90°
(-154,-334) → (-147, 1)       down the right side   → V2 tip
(-149, 0)   → (-308,-124)     diagonal up-left      → END
  • All turns are to the right.
  • The two corners are 90°.
  • The two V tips are ~128° turns: the new line goes back at a 52° angle to the old one. A normal PD follower cannot turn that hard in the space the sensors give it, so it overshoots the tip and loses the line.

Sensor geometry, from the world file:

  • The sensors are 31 px in front of the robot centre, at ±12.5 px to each side.
  • The line is 6 px wide.
  • So there is about a 7 px gap between the sensors where neither sees the line. That is normal: the robot is centred when both sensors see white.

3. Ports, sensors, polarity

  • Motors: M3 = left wheel, M4 = right wheel. Encoders: E3, E4 (same as the class robots).
  • Light sensors: A3 = left, A4 = right.
  • Polarity: black reads HIGH.
    • In the TRIK 2D model the light sensor returns 99 − brightness (source twoDLightSensor.cpp). White reads about 0 and black about 99.
    • On the real TRIK, the analog sensor is scaled from raw 30..1023 to 0..100. The classmates' formulas below only work if black is also HIGH there.
    • So the same code is used for both.
  • The program does not assume exact values. It only assumes black is higher than white, and it learns the actual range while it drives (see self-calibration).

4. What classmates did on the real robot

I read five classmates' lab-3 repos whose programs ran on the physical robot (KINGLABBOK, AdhambekYashnarbekov, Shahrizoda1120, nilufaroy, amaxmudova-ship-it).

All of them used block diagrams with the same structure:

A3_0, A4_0 = initial readings
loop (Timer ≈ 1 ms):
  err = (A4 − A4_0) − (A3 − A3_0)
  u   = Kp·err + Kd·(err − err_old)          Kp 0.7–1.3, Kd 8–15 (÷10)
  v   = base − 0.35·|err|                    base 25–30
  M3  = v + u ;  M4 = v − u

Facts taken from this:

  1. Ports: sensors on A3/A4, motors on M3/M4.
  2. Error sign: error is (right − left), and positive error speeds up M3 (left). So when the right sensor sees black, the robot turns right, toward the line. That only makes sense if black is HIGH and A4 is on the right.
  3. Speed: base around 30 works on the real robot.

My controller keeps exactly this sign convention and mapping (err = dr − dl, ml = v + u, mr = v − u). What I added:

  • calibration that adapts to the sensor range;
  • line-loss handling, which none of the classmates had. Their robots handled the gentle course in class but would lose the line at a 128° V tip.

I measured one classmate's encoder ratio from their data as ≈ 0.219 robot-degrees per unit of (E4 − E3). In the simulator it is ≈ 0.185. This matters for the sweep limit (section 9).

5. The algorithm

Every 10 ms the Function block runs these steps:

  1. Filter: exponential moving average of each sensor (A = 0.5) to reduce noise.
  2. Self-calibrate:
    • Keep a running minimum (white level) and maximum (black level) per sensor.
    • Normalise each reading to dl, dr ∈ [0, 1], where 1 = black.
    • The starting range is [reading − 3, reading + 25], so the scale is sensible before black has ever been seen.
  3. Detect: a sensor "sees" the line when its normalised value is above TH = 0.45.
  4. PD with speed reduction (while the line is seen):
    • err = dr − dl
    • u = Kp·err + Kd·Δerr
    • v = base·(1 − Ks·|err|)
    • left = v + u, right = v − u.
    The robot slows down when the error is large, which helps on bends. This is the "nonlinear" part.
  5. Remember side: whenever exactly one sensor sees the line, store which one in side (+1 = right, −1 = left). This is the direction the line went.
  6. Junction lock:
    • If both sensors see black, the robot is on a corner or V tip. Start a 150-tick (1.5 s) counter lockc.
    • While it runs, side is frozen, because readings while crossing a junction are ambiguous.
    • The forward coast is also skipped (step 7).
  7. Line lost:
    • Normal case: drive a gentle arc toward side for N1 + N2 = 150 ticks. This handles small slips on straights and corners.
    • Junction-lock case: only N2 = 30 ticks.
    • Then start the search.
  8. Search (bounded pivot):
    • Spin in place toward side, measuring rotation with the encoders: sd = E4 − E3.
    • If the robot has turned SWEEP = 750 units (≈139° in the sim) without finding the line, reverse direction and double the limit. That sweeps back through the start and as far again on the other side, then grows (750 → 1500 → 3000 …).
    • As soon as either sensor sees black, the PD takes over again.

6. Why the code has no if

The Function block in TRIK Studio uses a small expression language (qrtext / Lua-like). It has no if statement, but it does have min, max, abs and sgn. Two tricks build the logic from these:

TrickMeaning
max(0, sgn(x − T))1 if x > T, otherwise 0. A boolean.
c*a + (1 - c)*b with c ∈ {0,1}if c then a else b. A multiplexer.
c1 * c2, max(c1, c2), 1 − cAND, OR, NOT
max(0, n − 1)Count down to zero (timer)
(1 - seen) * (lost + 1)Count ticks while lost; reset to 0 when the line is seen.

So the whole state machine is a set of formulas that run every tick. There is no if/while, which works in the Function block and still generates clean JS or Python for the real robot (appendix).

9. How the V tip is solved

What happens at a V tip, step by step:

  1. Approaching the tip, the line starts turning right. The right sensor sees it, so side = +1.
  2. The turn is too sharp. The robot runs over the tip and both sensors see black for a moment, which starts the junction lock. While locked, side cannot change. Without the lock, the left sensor might be the last one to touch the line and the robot would search the wrong way.
  3. Now both sensors are on white past the tip. Because of the lock, the robot does not arc forward for 1.2 s, which would carry it far past the tip. After 30 ticks it starts the pivot.
  4. It pivots right. The new branch is ~128° away and the old line it came from is ~180° away. Stopping the first sweep at ~139° means the robot finds the new branch but cannot reach the old line. If the sweep were unlimited, a single wrong reading could make it lock onto the old line and drive back.
  5. If nothing is found (for example the side was wrong), it reverses with double range. That sweeps back through the original heading and covers the other side too, so the line is eventually found in every case.

The 90° corners usually work with plain PD plus the short arc; the search is a safety net there.

12. Running on the real robot

Not yet tested on hardware. Polarity and wiring are inferred from five classmates' working programs.

Checklist:

  1. Wiring: left light sensor → A3, right → A4, left motor → M3, right → M4. Upload V_shaped_line_follow_real.qrs.
  2. Place the robot on the line with the line between the two sensors. It calibrates from this first reading.
  3. Steers away from the line → sensors are swapped. Swap sensorA3 / sensorA4 in the first two loop lines.
  4. Spins or wanders on a straight line → this robot reads black LOW. Use (100 - sensorA3) and (100 - sensorA4) everywhere.
  5. Turns all the way back onto the old line at a V → lower SWEEP. Each robot has a different encoder-to-angle ratio; on the classmate's robot 750 ≈ 164°, so try ~640 (≈140°).
  6. Wobbles → lower Kp/Kd (e.g. 70/60) or base. Misses corners → lower base to 25.
  7. If a motor runs backwards, reverse it in the robot settings (or swap the sign of that motor block).

13. Likely professor questions

Which controller type is this — P, PI, PD, PID?
It is a PD controller with nonlinear speed scheduling (v = base·(1 − Ks|err|)) plus a state machine for line loss. There is no integral term: a line follower has no steady-state error to remove, and an I term winds up during line loss and corners.
Why do you normalise the sensors instead of using raw values?
The two sensors and different lighting give different raw ranges. Running min/max maps each sensor to 0..1, so err = dr − dl is fair. It needs no manual calibration step, only "black is higher than white".
What is the error signal and why that sign?
err = right − left. If the right sensor sees more black, the line is to the right, so the left wheel speeds up (M3 = v + u) and the robot turns right. This is the same convention as the classmates' working real-robot programs.
Why is the derivative not divided by dt?
The loop period is fixed (10 ms Timer), so dt is a constant folded into Kd.
Why two sensors close together if neither sees the line when centred?
That is the point: centred = both white, err = 0. When the robot drifts, one sensor touches the line and the error says which way to correct. The 7 px gap is a small dead zone that reduces wobble.
How do you know which way to turn after losing the line?
The variable side remembers which single sensor last saw the line. At a junction (both black) it is frozen so the crossing cannot corrupt it.
Why encoders in a line-following lab?
To measure how far the robot has turned while searching. Limiting the first sweep to ~139° guarantees it finds the 128° branch but never reaches the 180° old line. Without that limit the robot sometimes turned back the way it came.
Why no if statements?
The TRIK Function block language does not have if. Logic is built from sgn/max/min as 0/1 values, and c·a + (1−c)·b works as if-else (section 6). It still compiles to normal JS/Python.
How did you tune it?
Automated: the 2D simulator was run headless many times over parameter grids, different start poses and the "realistic" noise mode. Each run was scored by checkpoint order, and the most robust set was chosen.
Will it work on the real robot?
The ports, sign and speed match five classmates' programs that worked on the real robot. The new parts (calibration, search) only depend on "black is higher than white" and the encoders. The things most likely to differ are listed in section 12, with one-line fixes.
What happens at the end of the line?
The robot loses the line, searches, finds it and drives back along it. The task did not ask for a stop. A stop could be added (for example, stop after the second junction lock plus a lost timeout).
Limitations?
About 6% of noisy-sim runs fail (they lose the line early and circle). The SWEEP angle depends on the robot's wheel geometry. Calibration assumes the robot starts on a light surface near the line.

14. Note on the opencode MCP tool

opencode built an MCP bridge so an AI can drive TRIK Studio. I reviewed it.

It works for editing diagrams, but it has some bugs:

  • timeouts are retried, so commands can run twice;
  • there is a dangling buffer during script runs;
  • launch can return the wrong instance;
  • modal dialogs can block it.

It also has no headless "simulate" tool. Because of that, for testing I used the 2D-model command line directly (section 11).
